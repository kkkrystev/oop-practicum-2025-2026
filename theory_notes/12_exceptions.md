# Тема 12 : Изключения

Изключенията (_exceptions_) са механизъм за обработка на грешки, възникнали по време на изпълнение на програмата (_runtime errors_). Те позволяват грешката да бъде „пренесена“ от мястото (в кода), където е възникнала, към място (в кода), което знае как да я обработи.

**Обработка на грешки** наричаме процес, който позволява на програмиста да подготви програмата за случаи, в които възникват грешки по начин, който позволява на програмата да продължи своята работа надеждно и предсказуемо. 

Основната идея е да се отдели кодът, който реализира основната логика на програмата от кода, който обработва грешки.

Без exceptions често се налага почти всяка функция да връща специална стойност за грешка и извикващият код постоянно да проверява дали всичко е успешно. Това често може да води до:
- по-шумен и труден за четене код;
- дублиране на проверки;
- лесно пропускане на проверка за грешка.

Пример. Проблемът е, че програмата продължава работа, дори ако сме пропуснали проверката за грешка.

```cpp
#include <print>

double divide(double a, double b) {
	if (b == 0)
		return -1; // специална стойност за грешка
	return a / b;
}

int main() {
	double result = divide(10, 0);
	// if (result == -1) {
	//     // обработка на грешката
	// }
	std::print("Result: {}\n", result);
}
```

С exceptions грешката не може да бъде „игнорирана“ толкова лесно - ако не бъде обработена, програмата се прекратява чрез `std::terminate()`. *За това ще говорим по-късно в тази тема.*

Все пак exceptions имат и недостатъци:
- правят управлението на изпълнението по-трудно за проследяване;
- въвеждат runtime overhead при хвърляне на exception;
- усложняват low-level и performance-critical код;
- някои проекти и среди (embedded systems, game engines) ги забраняват напълно.

Затова в C++ exceptions са мощен, но не универсално предпочитан механизъм.
## 1. Хвърляне и прихващане

При работа с exceptions в C++ се използват три ключови думи:
- `try` - дефинира блок код, в който може да възникне изключение;
- `throw` - създава и “хвърля” обект, който описва възникналата грешка;
- `catch` - дефинира блок, който обработва хвърлено изключение със съвпадащ тип.

**Хвърляне на изключение** означава създаване и предаване на обект, който описва възникналата грешка. Това става чрез `throw`. 

**Пояснение за `throw`.**
Когато се изпълни `throw`, нормалният поток на изпълнение на текущата функция се прекъсва незабавно. От този момент нататък функцията не завършва по стандартен начин, а започва процес по търсене на подходящ `catch`. Обектът, който се подава към `throw`, се копира (или мести) и се използва като описание на грешката.

След като бъде задействан този механизъм, започва следващият етап от обработката - **stack unwinding**.
### Stack unwinding

_Stack unwinding_ е процесът на „развиване“ на call stack-а при напускане на функции. Това е процесът на премахване на function call frames от function call stack по време на изпълнение.

Stack unwinding започва, когато една функция прекрати изпълнението си. Локалните обекти, дефинирани в нейния стек биват унищожени в обратен ред на конструирането им. Една функция прекратява изпълнението си при срещане на `return` или на `throw` statement.

*В контекста на изключенията, stack unwinding гарантира, че частично изпълнен код не оставя “висящи” локални ресурси.*

**Важно.** Динамичната памет не се освобождава автоматично. Трябва ръчно да освободим динамично-заделените ресурси.
### Stack unwinding и изключения

Когато дадена функция (напр. `foo`) хвърли изключение и то не бъде обработено локално, започва връщане назад по веригата на извиквания. Ако функция `bar` е извикала `foo`, то ще се върнем в `bar`. Ако `baz` е извикала `bar`, връщаме се в `baz` и т.н.

На всяко ниво (или за всяка функция) проверява се дали има подходящ `try-catch`. Ако няма, продължава stack unwinding за текущия frame и локалните обекти се разрушават автоматично.
### Catch и обработка на изключението

Ако по време на това обратно движение по стека се достигне `try` блок със съвпадащ `catch`, процесът на stack unwinding спира и изключението се обработва там.

**Пояснение за `catch`.**  
`catch` дефинира блок код, който се изпълнява само ако хвърлено изключение със съвпадащ тип достигне до него. Той приема обекта на изключението като входен параметър. Синтаксисът `catch(...)` приема всякакви типове изключения.

Изпълнява се тялото на точно един `catch` - първият, който съвпадне по тип. 
### Ако няма обработка

Ако изключението не бъде прихванато нито на текущото ниво (*т.е. локално*), нито в нито една функция нагоре по стека, то достига до `main`. Ако и там няма съвпадащ `catch`, програмата се прекратява чрез `std::terminate()`.

`std::terminate()` е функция от стандартната библиотека, която се извиква, когато C++ runtime достигне състояние, в което няма валиден начин да продължи изпълнението (например: необработено изключение). По подразбиране тя прекратява програмата незабавно.
## 2. Видове изключения и наследяване

*Следващата секция може да ви се стори малко чужда, ако не сте запознати с темата за полиморфизъм.*

В C++ всички стандартни изключения са класове, организирани в наследствена йерархия. В основата на тази йерархия стои класът `std::exception`. Той е базов клас, от който наследяват всички стандартни exception класове. Това означава, че всеки стандартен exception обект е едновременно и обект от тип `std::exception`.

Този базов клас дефинира общо поведение (*интерфейс*) за всички изключения, които го наследяват. Основният метод е `what()`. Той връща текстово описание на грешката и може да бъде override-нат в наследниците.

*Списък с основните типове изключения, с които ще работим. Разбира се, има още полезни типове.*

| Грешка               | Описание                          |
| -------------------- | --------------------------------- |
| `std::bad_alloc`     | Невъзможност за заделяне на памет |
| `std::bad_cast`      | Невалиден cast                    |
| `std::runtime_error` | Грешка по време на изпълнение     |
| `std::logic_error`   | Нарушен инвариант на клас         |

По-рано споменахме, че се изпълнява тялото на първият `catch`, който съвпадне по тип". Също така, в тялото на един `try` можем да очакваме хвърлянето на изключения от различен тип. Затова catch блоковете се подреждат от най-специфични към най-общи.

```cpp
try {
    throw std::runtime_error("error");
}
catch (const std::logic_error& e) {
    std::cout << "logic_error\n";
}
catch (const std::runtime_error& e) {
    std::cout << "runtime_error\n";
}
catch (const std::exception& e) {
    std::cout << "base exception\n";
}
```
### Създаване на собствени exception класове

В реални програми стандартната йерархия често не е достатъчно изразителна. Затова се дефинират собствени класове чрез **наследяване от стандартните exception типове**.

```cpp
class MyException : public std::runtime_error {
public:
    MyException(const char* msg)
        : std::runtime_error(msg) {}
};
```
### `Catch` и object slicing

При обработка на изключения винаги се използва референция. Причината е, че изключенията са обекти, в чиято имплементация участва наследяване. Ако се прихване по стойност (по копие) се получава object slicing.

Пример. *Реалният обект `e`, може да бъде от тип-наследник (напр. `std::runtime_error)`.*

```cpp
catch (std::exception e)
```

Подаването по рефернция избягва object slicing, създаването на излишни копия и позволява коректната работа на метода `what()` (*тук става дума за полиморфизъм*).

```cpp
try {
    throw std::invalid_argument("Bad argument :(");
}
catch (const std::exception& e) {
    std::cout << e.what() << "\n";
}
```
## 3. Конструктори и деструктори

### Конструктори

Ако по време на конструиране на обект (в тялото на конструктор) се хвърли изключение, обектът не достига състояние на “напълно създаден”. Това означава, че неговият собствен деструктор няма да бъде извикан, защото обектът формално не е завършил конструкцията си.

Въпреки това, неговите части (базови класове и член-обекти), които вече са били успешно конструирани до момента на грешката, се разрушават автоматично чрез стандартния механизъм на stack unwinding, като техните деструктори се извикват в обратен ред на създаване.

Ако по време на конструиране се заделят ресурси ръчно (например чрез `new` или чрез отваряне на файлове/потоци), те няма да бъдат автоматично освободени при възникване на изключение. Трябва да освобождаваме всички ресурси преди да хвърлим изключението.

Освен това, ако имам множество `new` операции, които заделят памет, то може някоя от тях да хвърли изключение от тип `std::bad_alloc`. В такъв случай, трябва да "обезопасим" и това.

Пример. *В следващия пример разглеждаме конструктор на някакъв клас `MyClass`.*

```cpp
MyClass(int n, int m) {
	try {  
		a = new int[n];
		b = new int[m];
	} catch (...) {  
		delete[] a;  
		delete[] b;  
		throw; // препращаме изключението нагоре  
	}
}
```

Разбира се, най-четимо и най-правилно в повечето случаи е да се прилага правилото Rule of Zero - употреба на STL конейнери и smart pointers. По този начин, обектите сами ще се погрижат за изтриването на динамичната памет.
### Деструктори

В деструктор не трябва да се допуска хвърляне на изключение извън него. Причината е, че деструкторите често се изпълняват в контекст на вече активно изключение - именно по време на stack unwinding.

Ако в такъв момент (на stack unwinding) деструктор хвърли изключение и то не бъде прихванато вътре в самия деструктор, се получава ситуация с две едновременно активни изключения. Механизмът за stack unwinding не може да следи и обработва повече от едно изключение едновременно. В резултат програмата се прекратява чрез `std::terminate()`.

Допълнително, в модерните версии на C++ (*тези, на които работим*) деструкторите са `noexcept(true)` по подразбиране. Тоест, ако хвърлим изключение в деструктор и не го обработим локално, ще бъде извикана `std::terminate()`.  
## 4. Exception safety

След като една функция сигнализира грешка чрез изключение, важно е не само че е възникнала грешка, а и какво се случва със състоянието на програмата след това. В C++ това се описва чрез няколко нива на т.нар. exception guarantees, които показват колко стабилно остава състоянието при failure.
### Nothrow guarantee

**Nothrow** означава, че функцията няма право да хвърля изключение. Такова поведение се очаква напр. от деструктори, защото ако хвърлят по време на обработка на друга грешка, програмата се прекратява.

`noexcept` е оператор, който указва, че дадена функция не трябва да хвърля изключения. Това се проверява на ниво компилация. Ако функция, маркирана като `noexcept`, все пак хвърли изключение, програмата се прекратява чрез `std::terminate()`.
### Strong exception guarantee

**Strong guarantee** означава, че при хвърляне на изключение състоянието на програмата се връща точно както е било преди извикването на функцията. Няма частични промени. 
### Basic exception guarantee

**Basic guarantee** означава, че ако има грешка, обектът остава валиден и безопасен за използване, но може да е частично променен. Това означава, че всички ресурси са освободени коректно и инвариантите на обектите са запазени, но е възможно част от операцията вече да е била приложена.
### No exception guarantee

**No exception guarantee** означава, че при изключение няма никакви обещания за състоянието. Възможни са memory leak, частично модифицирани структури или нарушени инварианти. Това обикновено се случва при код с ръчно управление на ресурси без RAII и без защита при failure.
